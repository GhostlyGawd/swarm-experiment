# Independently pinned effect-policy signer: bounded research

**Status:** research and adversarial reproduction. Production integration lives in `src/tier2/effect-signer-anchor.ts`, `src/tier4/process-host.ts` and `src/tier4/process-deployment.ts`; this directory contains no production runtime. This work does not close V4-T2-04.

This document records the anchored V4 signer slice and its historical compatibility test. The later import-free V2 adapter artifact/V3 signed-policy profile is the fresh `scoped-anchored-v5` default; `scoped-anchored-v4` remains an explicit reopen profile with its original deployment `/4` and host-config `/2` bytes. See [adapter artifacts](../adapter-artifacts/README.md).

## Finding

The historical ProcessHost configuration included the policy digest and signer **name**, but omitted the signer's **public key**. `process-host-reopen.test.mjs` reproduces the consequence under the now-explicit `legacyEffectSignerTrust: 'factory-v1'` compatibility mode: open under key A, close, re-sign the identical policy body with key B under the same signer name, and reopen the same journal with key B. It succeeds. The policy body digest, manifest and old host configuration remain unchanged. The new anchored profile binds the independently provisioned public-key identity into host configuration `/2` and denies the substitution. A signature alone does not establish which signer is authorized; old histories require explicit compatibility selection and retain their original trust assumption.

Run: `node --test --experimental-strip-types roadmap/v4/research/effect-signer-anchor/*.test.mjs`. The isolated anchor tests cover key substitution, a changed candidate body, wrong signer name/repository/manifest/epoch, missing or changed pin, and malformed key/epoch. The separate ProcessHost test demonstrates the explicit legacy reopen behavior. Production regressions cover anchored refusal across real host opens, workers, sink calls and promotion.

## Production design

1. Provision an Ed25519 public key, signer ID and repository ID through a **trusted deployment option outside the reloadable services factory**. The pin must be supplied by operator configuration, a trusted secret/config service, or an authenticated admission root. A key read only from `deployment.json`, an artifact, a factory response, or the host journal is self-reported and does not solve this gap. Reject a missing independent pin for a new anchored profile. Canonical SPKI bytes and a domain-separated anchor digest identify the key.
2. Keep the current effect policy v2 signature and body validation. Before persisting genesis, registering a candidate, preparing a candidate, reopening an active/prepared host, or dispatching a live effect, verify policy signer ID, repository, AST root, manifest policy digest, policy epoch and signature against the external pin. The current epoch reader must also be independently provisioned and rollback protected; accepting the factory's epoch callback allows a stale policy to be replayed. The existing local `DurableGrantEpochs` checksum alone does not prevent whole-store rollback.
3. The reloadable factory supplies the signed policy and effect adapter, **never the trusted signer key or authoritative epoch**. Reject, rather than silently override, factory-provided trust fields. For an anchored profile, `ProcessDeployment.hostFor()` passes a copied trusted key and epoch reader to `ProcessHost`; `ProcessHost` checks them again when it opens and immediately before live sink dispatch. The candidate and the active source use the same external trust root. A concurrent trusted epoch change invalidates live calls before the sink.
4. Put the external anchor digest (or canonical SPKI fingerprint plus signer/repository identity) in a **new versioned host configuration identity**, deployment state and prepared record. Compare that identity on every reopen and promotion. The deployment-record field is a consistency pin only; external provisioning is the authority. A changed pin must fail before rewriting old records. The promotion effect plan already commits the candidate's policy digest; retain that link and add the anchored signer identity to the prepared/activation checks so a candidate cannot change key after preparation.
5. Keep existing `scoped-artifact-v4`, `scoped-signed-v3`, `scoped-v2` and `legacy-sealed-v1` histories reopenable only under their explicit historical profiles. Introduce an anchored profile for **new** deployments and a versioned host configuration domain. Never recompute an old host's `aether.process-host-config/1` as though it had pinned a key. Adoption of an existing v3/artifact history must be explicit and require external authorization, quiescence, exact source snapshot, old-history verification, independent pin verification and an admitted new deployment directory or signed migration record; retain old bytes and receipts. A changed key or missing pin is an error, not a fresh genesis.
6. Initial admission can use one pinned signer. Key rotation requires a separate, authenticated transition signed by the existing trust root or another external authority, a monotonic trust revision/epoch, an exact activation boundary and retained historical keys for audit. Do not infer rotation from a factory response or a new policy signature. Until this protocol exists, rotation is an explicit new-deployment migration, not an in-place reopen.

## Trust assumptions and limits

The operator's external anchor and epoch source are trusted; compromise of those authorities is out of scope. The research helper accepts an in-memory trusted key to make this boundary testable. It is not a secure provisioning service and does not itself stop an attacker who controls the process options. Production tests exercise promotion, restart and sink refusal, but do not establish a signer rotation ceremony, rollback resistance of the external epoch authority or complete all-path containment. Those remain open before V4-T2-04 can close.
