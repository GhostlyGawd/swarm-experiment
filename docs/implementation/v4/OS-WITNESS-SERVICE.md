# Process-external V9 witness service

The [witness service](../../../roadmap/v4/research/witness-service/README.md) is a separate Node process with an authenticated Unix socket and durable compare-and-swap heads for V2 effect, V1 host and V1 deployment witnesses. The controller supplies the existing V9 witness objects through `createProcessWitnessClient`; ProcessHost and ProcessDeployment require no service-specific path. The service binds exact authority, repository, deployment, operation/host and clock identities, checks HMAC on canonical bounded frames, refuses removal of previously witnessed records, fsyncs new head bytes and the storage directory, and rereads after publication. A lost response is uncertain; the caller must reread the head before any retry.

For local operation, provision a private 32-byte-or-longer key file and canonical configuration with absolute `socketPath`, `storageDir`, `keyFile` and namespace allowlist. Use `npm run witness:serve -- --config /absolute/private/config.json` in the service process. Configure exact identities where possible; `effect-scope` and `host-scope` authorize dynamically generated IDs only within the specified deployment namespace. Keep the service data outside controller-writable storage. If the service is unavailable, V9 state reads and publication fail closed. Restart with the same key, namespace and durable directory; do not clear or replace the witnessed heads to get past a stale or divergent result. The CLI probes and removes only a stale Unix socket when the former listener is gone.

The [separate-process protocol test](../../../roadmap/v4/research/witness-service/witness-service.test.ts) checks authenticated frames, all three head types, stale CAS, wrong namespace/key, duplicate live service, SIGKILL and exact restart recovery. The [real V9 host/deployment test](../../../test/tier4/process-wasm-external-witness.test.ts) routes signed traffic through a [native peer-credential gateway](../../../roadmap/v4/research/witness-peer/README.md), kills the service after completed calls, observes fail-closed reads, restarts it and verifies cached results without another broker dispatch. Correctly authenticated attempts to remove actual witnessed broker, host or deployment records are refused. A separate [controller crash test](../../../test/tier4/process-wasm-controller-crash-witness.test.ts) keeps the witness service alive, SIGKILLs a real ProcessHost controller after the broker recorded a committed read-only Wasm effect, and recovers in a fresh controller process. Safe abort is refused; replay returns the exact result with one guest dispatch. These tests run under **one UID**. They establish bounded process crash durability on this machine, not independent custody against hostile code with the same UID or commitment of an external sink.

For a production containment claim, the witness must run under a dedicated UID with its keys and head directory owned by that UID; the trusted broker/controller and untrusted adapters need distinct enforced identities. The socket should live in a witness-owned directory that clients cannot modify. macOS checks directory traversal and Unix socket write permissions at connect, and `getpeereid(3)` can attest the peer's effective UID/GID at connection establishment. [Apple `connect(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/connect.2.html), [Apple `getpeereid(3)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/getpeereid.3.html). Node's public `net.Socket` API does not expose that check; the native gateway adds it and forwards only bounded frames to the private service socket. [Node 26 `net` documentation](https://nodejs.org/download/release/v26.7.0/docs/api/net.html). This gateway has not yet been qualified with distinct provisioned UIDs or hostile adapters.

The service checks canonical identity, size, revision and retained operation inventory, but does not independently prove every host/deployment transition or an external sink's actual commitment. HMAC possession also does not confine hostile JavaScript running in the trusted controller UID. Separate UID custody with the native peer check, protected operator keys, authenticated sink status, replay witnessing, and rollback resistance across whole-machine restores remain open. T2-04/G1/G2 and NFR-16 remain unverified.

Availability remains bounded: the native gateway serves one exchange at a time with a deadline, the synchronous client starts a transport subprocess per operation, and the immutable service lock ticket log needs quiescent maintenance after 10,000 launches. These are operating limits, not release performance qualifications.
