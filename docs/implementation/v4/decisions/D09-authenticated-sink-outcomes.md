# D09 — Authenticated sink outcomes

Status: opt-in implementation profile under V4-T2-04; release qualification open. Specification 0.1.0 and historical V1/V2 broker formats are unchanged.

## Decision and contract

The witnessed V2 broker journal proves which bytes the broker retained. Its public `aether.effect-receipt/1` digest does not prove that an external sink committed those bytes. The opt-in V3 broker requires an operator-pinned Ed25519 [sink anchor](../../../../src/fabric/sink-receipt.ts), a namespaced V2 effect witness, a deployment ID and an approved adapter artifact digest. It writes `effects-v3.json` as `aether.effect-journal/3`, with an exact signed sink receipt on each terminal post-dispatch event. V1/V2 files are never silently adopted.

The version 1 sink receipt binds repository and deployment, execution/effect IDs, exact request and payload digests, grant reference, policy epoch, sink authority/key epoch, approved adapter artifact, terminal disposition and committed value digest. The broker verifies it against its own request and operator anchor before publishing committed success or a sink-confirmed abort. It rechecks the retained receipt on journal read, cached result and replay. Unknown status or malformed/contradictory proof leaves the effect indeterminate or fails closed.

The [trusted adapter wrapper](../../../../src/fabric/attested-sink-adapter.ts) calls `execute` once after the broker's durable dispatch marker. Its `status` path is read-only with respect to a committed operation. A `not_committed` reply is terminal only with a signed, durable fence that prevents a later execute for that same logical effect. Transport failure is `unknown`, never evidence of noncommit. The sink uses `(repositoryId, executionId, effectId)` as its idempotency key across deployment generations. A new deployment attempting to reuse a prior ID gets a conflict and must recover through the original deployment-bound receipt; it cannot create a second commit.

The bounded [sink service fixture](../../../../roadmap/v4/research/attested-sink/README.md) stores its append-once effect record, result and exact signed receipt in one fsynced atomic state replacement before responding. A status request returns the identical committed receipt after restart, or first writes a terminal signed fence if no operation exists. The service has a 64 KiB receipt/request-value domain and a 192 KiB outer response frame so an accepted near-limit value remains recoverable. The private Ed25519 signer stays in the sink process. The trusted controller receives an operator-supplied public anchor **and** a transport HMAC credential with execute authority; the latter must not reach untrusted adapters.

### Versioned sink decision custody

The opt-in `aether.attested-sink-config/2` profile adds a separately launched, operator-configured sink witness. Its `sink-scope` pins the full public anchor and adapter artifact digest. The `aether.sink-state-witness/1` identity binds those subjects without a deployment ID; its `/2` sink journal retains the complete ordered decisions. Each revision adds exactly one row. The witness independently validates every signed receipt, value, request, sequence and unique logical effect ID before its durable compare-and-swap. The sink writes the witness head **before** its local `sink-state-v2.json` mirror and response. A lost CAS response is settled only by rereading the exact candidate head. On restart or a later request, a missing or older local mirror is restored from that head; equal-revision disagreement and local state ahead of the witness refuse service. Existing `/1` state cannot be silently adopted into `/2`, and `/1` refuses to open a `/2` mirror.

The witness socket, key and storage need separate operator custody from the sink's writable store. The CLI rejects a witness socket/key inside that store and requires a different transport key; the current process fixture still runs under one UID, so this is not evidence of distinct-UID custody or resistance to a privileged actor rolling back both stores. The `/2` profile protects the fixture's decision inventory against rollback of the **sink's local file alone**. It does not establish atomicity with an arbitrary external service.

### Broker replay bound to sink custody

An opt-in V4 broker pairs a namespaced effect witness with the operator-selected sink state witness. It records `aether.effect-journal/4` in `effects-v4.json`, including the sink witness digest, while V3 keeps its original journal and file. Before a committed result or terminal noncommit fence is published, the broker verifies the signed receipt and finds that **exact request, value and receipt** in the sink witness head. The same check runs when a saved outcome is read or replayed. A valid signature absent from the sink head remains indeterminate; witness outage cannot be treated as noncommit. A V3 broker refuses an existing V4 file, and a V4 broker refuses an existing V3 file.

This adds a read dependency on the sink witness for terminal cached outcomes. Its availability and custody are part of the V4 broker trust boundary. The effect witness validates the V4 journal's versioned binding and immutable receipt history, while the broker checks the independently selected sink head. The bounded fixture uses separate sink and witness processes under one UID; it still does not prove that an unrelated external service performed an irreversible transaction.

## Evidence boundary

The [real controller crash test](../../../../test/fabric/attested-sink-broker-crash.test.ts) kills a controller after the sink stored a commit but before broker terminal publication. It covers both the historical V3 and opt-in V4 broker. The V4 run uses a separate process for the sink decision witness, deletes the sink-local mirror before restart, then reconciles in a fresh controller against the retained head. It checks cached retry, signed noncommit fencing, legacy downgrade refusal and denial of a cached result while the sink head is unavailable. A [targeted broker test](../../../../test/fabric/attested-sink-adapter.test.ts) returns a valid signature without a witnessed decision; V4 stays indeterminate until the exact signed decision is appended to the sink head. Focused receipt, adapter, service and broker tests reject forged/wrong-context proofs, cross-deployment duplicate commits and response loss.

This fixture's external operation is an append-once sink state record, not an arbitrary third-party API. A truly independent sink must enforce the same effect ID and receipt atomically with its actual irreversible transaction, retain status across service and machine recovery, validate authorization beyond possession of the HMAC key, protect its signing key under a distinct authority, and provide an authenticated read-only status or fenced noncommit. The fixture's approved adapter digest is a test label, not measured signed executable bytes. ProcessHost/ProcessDeployment signed profile integration, distinct-UID custody, general hostile-adapter isolation, budget settlement under sink uncertainty, key rotation and the full grant-path campaign remain open. V4-T2-04/G1/G2 and NFR-16 are not verified.
