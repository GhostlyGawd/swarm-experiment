# D12 — Budget settlement from witnessed sink decisions

Status: bounded broker and direct ProcessHost implementation under V4-T2-04 and prerequisite research for V4-T2-05. Specification 0.1.0 and all release thresholds remain unchanged.

## Decision

The [attested sink budget evidence helper](../../../../src/tier2/attested-sink-budget-evidence.ts) supplies `ResourceBudgetBridge.observe` and `ResourceBudgetLedger.verifySettlement` from an operator-pinned sink public anchor and branded `/2` sink state witness. It pins repository, deployment, approved adapter artifact label, ledger digest, owner, one fixed conservative charge and a bounded set of **full expected requests**. No two declarations may share the ledger's five-field effect binding. It reads the complete witnessed sink decision, checks the exact request/value/receipt and Ed25519 signature, then returns a committed observation with the fixed charge or a signed terminal noncommit fence. Missing rows, witness outage and rollback are unknown; a conflicting request under the same logical effect ID or binding is refused.

The ledger verifier independently decodes the bridge's outer settlement witness and compares the ledger, owner, **full request digest**, basic binding, disposition, value, charge and canonical inner receipt to the current sink witness head. A caller's receipt digest or `observe` claim alone cannot debit or refund the ledger. A stable policy digest covers the pinned repository, deployment, anchor, witness, adapter artifact, owner, fixed charge and complete expected-request inventory. It can be computed before ledger creation and is included in the ledger identity when historical revalidation is enabled. The full request declarations must be independently allocated and retained by the operator; this bounded profile does not itself prove which pre-split handle a direct ledger caller used. A committed fixed charge is not a measurement of actual tokens, dollars, time or memory used by an arbitrary service.

## Tested broker path

The [real-process integration test](../../../../test/tier2/attested-sink-budget-broker.test.ts) uses a separate sink and sink-witness process, the V4 signed broker, a pre-split durable budget ledger and bridge. The broker reserves before the sink call. A witnessed commit charges once; cached retry and reopened ledger/bridge do not charge again. The ledger's opt-in `revalidateSettlementOnRead` mode rechecks historical signed decisions on reopen and every read. The mode and policy digest are bound into its ledger identity; reopening with revalidation disabled, a different fixed charge or a shorter request inventory fails. A second effect receives a signed `not_committed` fence before broker reconciliation and refunds the unused reservation. An early sink-witness outage prevents broker admission before reservation. An outage after the broker's durable dispatch marker leaves a third reservation inflight; it is not refunded from absence or timeout. Once the witness restarts, signed status creates a terminal fence and recovery refunds exactly once.

The bridge's generic pre-dispatch release hook is not, by itself, evidence of noncommit. This helper refuses to verify a refund without a signed sink fence. Opt-in historical revalidation also makes ledger reads unavailable when the sink witness is down.

## Witnessed V5 broker and direct V12 host admission

The V5 broker pins a branded, separately witnessed resource bridge to the signed sink authority, exact non-null reservation and complete effect request. It publishes an effect journal `/5` and event `/4`; the operator effect witness retains the bridge profile digest and V5 recovery transitions. The broker reserves before sink dispatch, checks the exact signed sink disposition before consume/refund, and leaves an uncertain reservation encumbered if the sink or budget witness is unavailable. A terminal cached result is returned only after the bridge and ledger settlement receipts revalidate against the signed sink witness. Reserve receipt loss after the ledger has applied a reservation is treated as indeterminate and reconciled, not as an unreserved error.

The direct ProcessHost budget profile has configuration `/11` and retains the existing witnessed host journal layout. An operator provisions the initial heap, operation ID, exact signed target, reservation and complete effect request before constructing the host. Grant reference `/3` binds the signed rule path and sink/budget independent identities without the final host configuration, avoiding a digest cycle. The host recomputes the exact request from the worker's tagged arguments and retained recovery record, then compares it with the operator inventory before adopting the proposed snapshot or reserving funds. The host configuration pins the budget authority, bridge profile and evidence policy. Admission checks that the bridge and ledger have external monotonic witnesses and that the selected evidence policy is the one embedded in the ledger identity. The reloadable adapter factory cannot substitute the bridge through its router options.

The direct host campaign exercises a real worker and separate sink, sink witness and operator witness processes. It checks wrong-target denial before reserve, one fixed charge for a witnessed commit, retry/reopen without double charge, a signed noncommit fence and refund, forged bridge-profile rejection by the effect witness, and cached-result refusal during sink witness outage. All processes still run under one UID. This is a bounded fixed-charge profile with predeclared requests, not measured tokens, dollars, time or memory for general adapters.

The ledger's generic verifier callback and policy digest are selected by the process holding its signing key; matching the digest does not authenticate substituted callback code. Distinct-UID custody and independently validated witness transitions, a real third-party irreversible transaction, full direct/closure/cross-process/deployed effect coverage, deployed budget selection and promotion, atomic revocation/result publication, general payload target semantics and actual usage metering remain open. The V5 broker admits live mode only; isolated replay needs a separate read-only profile. This checkpoint does not close T2-04, T2-05, NFR-16 or any financial performance gate.
